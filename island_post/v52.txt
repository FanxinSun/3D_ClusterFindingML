  Why the checks were fast:

  - The branch list (69 vs 10 vs 91) is file metadata — ROOT stores the tree
  structure in a header, so listing it reads a few kB, no event data at all.
  - The min/max spot-check read actual data, but ROOT is columnar: each branch
  lives in its own compressed baskets, so scanning rawmbd over 300k rows reads
  only that branch's few MB, not the 376 MB file. Forty branches × 300k rows ≈ a
  few seconds of decompression.

  Nothing wrote to the files — TFile::Open defaults to read mode, and the
  zero/NaN branches were zero/NaN at production time (islandize91 wrote them
  that way because the sim has no DAQ/tracking source for them).

  If we ever did want to genuinely refill those branches, the cost depends on
  the stage, not the whole chain: the 91-branch cluster tree is produced by
  islandize91.C reading the digi file, so repopulating (say, stamping the
  composer's rate/trigger info into the scaler branches) would be a re-run of
  just that clustering stage — minutes on the existing 595 MB digi file. The
  expensive path (Geant4 → transport → composer → readout, the ~22 min+
  production) only has to rerun when something upstream of the stage changes.
  That staging is exactly why the readout-only versions in the manifest (v3.3,
  v3.4, revB/revC) exist as cheap iterations on frozen frames.

● What boundary windows are — corrected by today's fingerprint: they are
  end-truncated readout slices. sPHENIX runs a hybrid triggered-streaming DAQ:
  the TPC is read out continuously and gatelessly (SAMPA defines event
  boundaries offline), and because the full stream is ~10× the 300 Gb/s budget,
  only trigger-correlated slices of the stream get saved. Normally a slice spans
  the full ~106 μs (970 tbins) after the trigger. In 15–18 of your 100 events,
  the recorded slice ends around tbin 400–450: content fills the first ~45% of
  the window and the last half is exactly empty. Everything anomalous about them
  follows from that one cut: zero beyond-membrane content (those hits are
  collisions ≳28 μs post-trigger arriving at tbin ≳510 — the truncation removes
  them by construction), reduced totals (81k vs 277k px/event ≈ the truncation
  fraction), and their scatter through the run (each DAQ throttle/pause or
  segment boundary cuts whatever slice is in flight — note your file is
  literally segment -0). So "boundary window" = a trigger whose stream slice hit
  a DAQ boundary.

  Existing models online: I found the architecture documented but no published
  model of the truncation itself — which is expected, since it's a
  DAQ-operations artifact rather than physics:

  - The sPHENIX TPC design paper (Klest) documents the continuous, gateless
  SAMPA readout with offline event-boundary definition and the out-of-time
  pileup implications of drift time ≫ bunch spacing.
  - The sPHENIX real-time-AI paper documents the hybrid triggered-streaming DAQ,
  the 300 Gb/s ceiling, and that only ~10% of the stream is saved — the reason
  slices exist at all. Busy/throttling machinery is standard (e.g., the laser
  system fires through a tunable standalone busy).
  - The closest established treatment is ALICE Run 3: their continuous TPC
  readout is chopped into TimeFrames, and incomplete TimeFrames at boundaries 
  are simply dropped from physics processing. That's the precedent for our
  "steady subset" choice.
  - The most likely place this exact effect is discussed for sPHENIX is the run
  mailing list (a 2024 DAQ/bandwidth workfest thread exists), but it's behind
  the collaboration login — your supervisor can read it; asking him "we see ~15%
  of events with the TPC slice ending mid-window — throttling or segment
  boundaries?" is now a sharply-posed question with evidence attached.

  For the pipeline, the two options stand, now with the correct mechanism:
  exclude them from anchors (the ALICE-style choice — the steady-subset numbers
  I computed are exactly this), or add a composer end-truncation mode (truncate
  the readout at a cut tbin drawn from the measured distribution, p≈0.15) if you
