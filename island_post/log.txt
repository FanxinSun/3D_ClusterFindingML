  GL1 = the sPHENIX Global Level-1 trigger — the central trigger processor. It
  takes the detector trigger inputs (MBD, ZDC, calorimeters …), makes the accept
  decision, and hands it to the DAQ through the GTM (Global Timing Module);

  trigger scalers — the rawmbd / livembd / scaledmbd / rawzdc … columns in

  a GL1-issued trigger, and offline (LaserEventIdentifier::isGl1LaserEvent,
  DiffuseLaserEventSelector) tags laser events from that GL1 packet. So
  "laser-triggered event" means: the readout window was opened by the laser
  trigger, which is why the flash sits at a fixed sample (~329) inside the
  window instead of at a random one.

● The bimodality is a window-statistics mixture, not a detector feature: the 
  ~500–800 µm shoulder is the sparse-window population (windows with ≤9 pixels),
  and only real data has enough of them to show it. Sim reweighted to the real
  pixel-count mix reproduces the whole shape — shoulder fraction 23.7% vs real's

  Figure: sim_validation_plots/lsag_probe_v6.png (producer
  island_post/lsag_probe.C; windows rebuilt exactly as nf_digipix's — same 4-row
  sliding construction, gate, fitter, road, ev44 veto; all panels
  zoom-checked).

  The mechanism, in three steps

  1. Window RMS scales hard with pixel count n — real medians 754 / 1000 / 1210
     / 1579 µm for n = 5-6 / 7-9 / 10-14 / ≥15 (sim shows the same trend:
     535/834/1088/1364). Two effects stack: the dof factor √((n−3)/n) (a 5-point
     circle fit with 3 parameters half-overfits — the ~1% of windows in the
     near-zero bin are the extreme of this), and wider clusters carrying both
     more pixels and more intrinsic spread.
  2. Real's n-mix is bimodal-making, sim's isn't: n≤9 windows are 35.3% of real 
     vs 1.8% of sim (real med n = 12, sim 24). The n≤9 classes peak at 750–1000

     6.67 sim — not missing rows (3-row windows: 34% vs 29%), the same ×2 as the
     standing px/track gap (124 vs 266).

     single peak into the real two-mode outline (gray dashed in panel 1),
     shoulder 23.7% vs 21.9%.

❯ what is 3σ?                                                                   

● 3σ = the outlier cut in the clip: a pixel is dropped if its residual to the 
  fitted circle is more than 3 robust standard deviations away from the track's 
  own residual core. Concretely, in island_post/gtail_probe.C:44 (trimFit,
  reused by lfloor_probe.C), repeated 3 times:

  1. fit the circle, compute each pixel's residual (distance to the circle);
  2. estimate the core spread robustly: σ = 1.4826 × MAD, where MAD = median
     |residual − median residual| (for a Gaussian, 1.4826×MAD equals the
     standard deviation — but unlike the RMS it is not inflated by the very
     outliers you're hunting);
  3. drop pixels with |residual − median| > 3σ (with a 500 µm floor, and never
     trimming below the 12-px fit bar), refit.

  For Gaussian scatter, ±3σ contains 99.7% of points — so a clean track loses
  essentially nothing (sim lost 0.0% of pixels, median), while a second track's
  pixels sitting ~10 mm off inside the 1.2 cm road are tens of σ out and get
  removed (real lost 3.1%). That asymmetry is why the clip is a diagnostic that
  separates association pickup from genuine track content rather than a tuning
  knob.

❯ what is "asymmetric grouping"? what is "road"                                 

● "Road" is standard tracking jargon: the search corridor around a seed 
  trajectory within which hits are collected. Concretely in our meter
  (ms_nofinder.C:174, realPixGroups): a real pixel is attached to a track if, in
  the same event and same pad layer, it lies within 1.2 cm in xy AND ±6 tbins
  of any of that track's seed clusters (first matching track wins, each pixel
  joins one track). Picture a 1.2-cm-radius tube following the track through the
  TPC: everything inside joins the track — including, in a pileup event, pixels
  that actually belong to a different particle passing nearby. That is the
  "road pickup" that made the global-fit tail.

  "Asymmetric grouping" is my shorthand (not standard jargon) for the fact that
  in the no-finder meter the two sides of the real-vs-sim comparison were built
  by different rules:

  ┌──────┬──────────────────────────────────────────────┬───────────────────┐
  │ side │         how pixels become a "track"          │ can wrong pixels  │
  │      │                                              │      get in?      │
  ├──────┼──────────────────────────────────────────────┼───────────────────┤
  │ real │ tracker seeds (ntp_clus_trk) + the road      │ yes — anything    │
  │      │ above                                        │ inside the tube   │
  ├──────┼──────────────────────────────────────────────┼───────────────────┤
  │      │ truth label (gtrackID: each digi pixel is    │ no — by           │
  │ sim  │ tagged with the particle that made it,       │ construction      │
  │      │ ms_nofinder.C:1039)                          │                   │
  └──────┴──────────────────────────────────────────────┴───────────────────┘

  So a real track group could carry another particle's pixels while a sim group
  never could — and any real-vs-sim difference then mixes two things: genuine
  detector differences and the difference between the two grouping methods. The
  1.53 global ratio was mostly the second.

  "Symmetric grouping" = same algorithm on both sides. That's what the last
  probe did: the exhaustive finder + the same road applied to real and sim — at
  which point sim caught wrong pixels at the same rate as real, and every
  before/after metric came out equal (g/l 1.35 vs 1.34). Same conclusion from
  the other direction as the 3σ-clip test: make the association fair — either by
  removing the pickup on both sides or by inflicting it on both sides — and
  real and sim agree.
