● Yes — F is an out-parameter, so the caller's F is overwritten by fitCircle the
  moment line 123 runs, regardless of what fitBar returns afterwards.

  Fit &F is a non-const reference, so F = fitCircle(G.x, G.y) copy-assigns into
  the caller's object (all six members — fitCircle returns by value, so there's
  no partial update). The bool is only the verdict; the fit itself is delivered
  through the reference. That's precisely why the callers can read F.rms / F.R
  right after the continue guard.

  What F holds on a false return depends on which return false fires:

  ┌──────────────────────┬──────────────────────────────────────────────────┐
  │         exit         │                 F after the call                 │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ ms_nofinder.C:119 (< │ untouched — default-constructed zeros, ok=false  │
  │  12 points)          │                                                  │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ ms_nofinder.C:122    │ untouched — same                                 │
  │ (span < 15 cm)       │                                                  │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ ms_nofinder.C:124    │ already overwritten with a real but rejected fit │
  │ returns false        │  (ok=true, R outside [45, 2e4), or a degenerate  │
  │                      │ ok=false from a singular det / r2<=0)            │
  └──────────────────────┴──────────────────────────────────────────────────┘

  So "rejected by the R cut" and "rejected by the bar cut" leave F in two very
  different states, both reported as the same false.

  That is not a bug at any current call site:

  - All five if (!fitBar(...)) continue; sites (:172, :249, :331, :361, :440)
  declare Fit F; inside the loop body, so a rejected fit dies with the iteration
  — nothing stale carries into the next group.
  - The one site that survives a false return, :470 bool pass = 
  fitBar(kv.second, F);, only reads F.a/F.b under if (pass && ...) at :478, and
  F is likewise fresh per iteration at :469.

❯ ok, since we use (event, seedID) pair as the identification, why sidely use   
  ev*100+layer as the bucket index? why involve layer?                          

  Ran 1 shell command (ctrl+o to expand)

● Because the two keys answer different questions.

  seedIdx is identity: given a cluster, which track does it belong to. bucket is
  a search index: given a raw ntp_hit pixel, which clusters could it possibly
  belong to. You can't key that by seed — the pixel's seed is precisely the
  unknown the road-match is solving for.

  Layer is the right pruning dimension for two reasons:

  1. Physical. A pixel in pad row L can only be part of a cluster in pad row L.
  Clusters don't span layers, so any candidate outside the pixel's own layer is
  wrong by construction.
  2. The road is wider than the layer spacing. Measured on this ntuple, the
  radial pitch between adjacent layers is 0.563–1.942 cm, mean 0.933 — while the
  road cut at :234 is 1.2 cm in x–y. So a pixel is routinely within 1.2 cm of a
  cluster one layer in or out. Without the layer key those neighbours would be
  live candidates and would steal pixels.

  The speed effect (candidates drop from all clusters in the event to ~1/48 of
  them) is a bonus, not the reason.

  Related, since you're reviewing: :239's break makes it first-match-wins within
  the bucket, not nearest-match. Bucket order is ntuple order, so with a 1.2 cm
  road a pixel goes to whichever qualifying cluster was written first, not the
  closest one. Inside a single layer that's usually the same cluster, but not
