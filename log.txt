❯ If I have a second set of real data, will the sim pipeline optimization be    
  much easier?                                                                  

● Yes — but how much easier depends almost entirely on what's different about
  it, not on having twice the events. A second condition is worth far more than
  a second sample, because the hard part of this whole campaign was never
  statistics — it was degeneracy: one dataset gives one point in condition
  space, and several very different explanations produce the same observables at
  a single point.

  Ranked by how much leverage a second set would buy:

  1. Same species, different collision rate — breaks the worst degeneracies we
  have. The envelope, pileup structure, CV, and the post-trigger oot population
  all scale with rate in predictable ways, while per-collision content does not.
  Two rate points would let us derive the time axis instead of fitting it, and
  would directly test the two load-bearing attribution claims of v5.3: that the
  content deficit was generator-owned (it should be rate-independent) and that
  ⟨size⟩ is response-owned (it should stay rate-flat). The w1 early-region floor
  we just accepted would also become diagnosable: a pre-window rate shape is
  either shared between runs or it isn't.
  2. Anything with resolved DAQ bookkeeping (untruncated, or truncation
  documented) — kills the single biggest ambiguity outright. The entire
  dual-reference regime — every figure in two versions, the ±26% vs ±1% split —
  exists only because we cannot decide from inside one dataset whether the 38
  truncated events are bookkeeping or physics. One clean set makes that a
  measurement instead of a standing question.
  3. Different species (OO/AuAu) — the cleanest separator for what's left. The
  declared response family (sh/hi +17.5%, run tails, size/islands fragmentation
  dual, radial tilt) is detector-side and must be species-independent. Whatever
  moves with species is generator physics; whatever stays is response. That
  splits the remaining residual list in one shot — and AuAu occupancy would
  stress-test the ZS/dead-map/saturation modeling in a regime pp never reaches.
  4. Different trigger config or min-bias — turns ε_MBD from a fitted quantity
  (our 0.588 ± 0.033 scan, your protocol) into a directly measured one.
  5. Just more events of the same run — the weakest case: floors shrink by √2,
  the complete subset grows, tails firm up. Helpful, not transformative — every
  degeneracy survives.

  Two honest caveats. First, a second set doesn't shrink the work per dataset —
  per-run knobs (envelope, rspec, ε, anchor) get re-derived for it — but that
  machinery is now a ~day of turnkey pipeline, so the marginal cost is low; what
  it multiplies is constraints on the shared knobs (electronics, transport,
  tune). Second, and maybe most valuable: a second set is the out-of-sample test
  we currently don't have. With one dataset there's a standing risk that some
  of our "physics" knobs quietly absorbed run-79507 quirks. If v5.3b's response
  family transfers to a second run unchanged, the model is real; if it doesn't,
  we find out where we overfit — either answer makes the next optimization round
  sharply easier. (Same logic applies downstream to your ML labels: a model
  trained on one condition needs exactly this kind of second condition to prove
  it generalizes.)

  So if you get any say in what the second set is: ask for a different rate or a
  bookkeeping-clean run first, a different species second.

● Why the design doesn't allocate a momentum per hit coordinate — three reasons,
  in order of weight:

  1. The local momentum is already stored — as geometry. In a known field, the
  local pT is the local curvature: pT = 0.3·B·R. The truth hit positions (which
  we do store per hit) encode it completely, and that's exactly how our own
  validation extracts it — truth_circle fits circles to truth hits and compares
  R_fit against R_exp(creation-pT), and mcs_split measures momentum-dependent
  scattering purely from split-arc tangents. Storing local p⃗ per hit would add
  no information the positions don't carry, at three floats per row on ~10⁸-row
  tables.
  2. Creation-pT is the canonical track parameter. It's the number
  reconstruction is judged against, the looper-cut variable, and the
  label-defining quantity — a per-track property, not a per-hit one.
  3. Schema fidelity. The whole hit69/CSV discipline mirrors the container
  evaluator layout so sim and real ntuples stay drop-in comparable; the truth
  block's one-row-per-track shape is part of that contract.

  Where your instinct is physically right: the single value is exact at creation
  and a genuine approximation along the path — negligibly so for GeV tracks
  (gas dE/dx gives Δp/p ~ 10⁻⁴ across the TPC), but measurably for the sub-100
  MeV curlers, which really do spiral inward as they lose energy. The
  one-pT-per-track design is weakest for precisely the looper class.

  If per-hit (or per-cluster) local pT is ever wanted, two paths, neither 
  touching the frozen semantics:
  - Derive it (no rerun, no schema change): sliding-window circle fit over each
  truth track's stored hits → local R → local pT. Exact up to MCS, available
  today.
  - Add it (additive columns): write the pre-step momentum into new branches
  (e.g. glpt) in the SD writer — transport keeps reading the old columns so
  nothing recalibrates — then a small exporter join attaches cluster-local pT in
  ntp_clus_trk. Costs one G4 library regeneration (~hours).

  If the motive is ML features or labels (fast section vs slow section of the
  same curler), that's the ML thread's call to request — from this side I'll
  just confirm: the information exists, and path (b) is one additive schema
  change away.

❯ OK, so the sim, Creation-pT is also one scalar value for one track, how can   
  you derive for each hit                                                       

● From the geometry — the per-hit positions are stored, and in a magnetic field
  the local momentum is the local curvature. The field makes the momentum
  readable off the trajectory at every point: pT[GeV] = 0.3·B[T]·R[m], so at our
  B = 1.4 T, pT = 0.0042 · R(cm). One scalar per track is what's stored; the
  per-hit values are encoded in the hit coordinates.

  The concrete recipe (pure post-processing on the existing ntp_g4hit, no
  re-simulation):

  1. Group and order: collect all hits of one (event, gtrackID), sorted by gt
  (the G4 step time) — that gives the trajectory in flight order.
  2. Sliding window: for hit i, take its neighbors i−k … i+k (k ≈ 3–7).
  3. Local circle fit in the transverse plane (gx, gy): either an algebraic
  circle fit over the window, or minimally the three-point Menger form — for
  points A, B, C with triangle side lengths a, b, c and area S: R = abc/4S. That
  local radius gives pT(i) = 0.0042·R(i).
  4. Total momentum, if wanted: the dip angle from the same window, tan λ =
  Δgz/Δs_xy (rise over transverse arc length), then |p|(i) = pT(i)/cos λ. Charge
  sign, if wanted, from the rotation sense (sign of the cross product along the
  window).
  5. Per-cluster local pT (the useful export): average the per-hit values over
  the truth hits that feed each cluster, joined through the existing ntp_truth
  association — that's how a local_pt column would ride into the cluster tables.

  Why this is trustworthy rather than a rough trick: truth hits are exact — no
  detector smearing, micron-level step midpoints — so the only "noise" in the
  local fit is real physics (MCS kinks between steps). We've already validated
  exactly this estimator in our own machinery: truth_circle fits circles to
  truth hits and recovers R_fit/R_exp(creation-pT) = 0.9992 on whole tracks, and
  mcs_split resolves mrad-level tangent changes from sub-arcs. The window size
  is the one real knob: short windows are more local but feel individual MCS
  kinks; longer windows average the kinks and track the secular momentum loss —
  which is the signal you're after. Expected per-hit precision is at the few-%
  level, far finer than the tens-of-% spiral-down a curler undergoes.

  Where it works best is exactly where it's needed: the curler population. A 100
  MeV pion has R ≈ 24 cm — strong curvature, a precise local fit, and genuine
  momentum evolution along the spiral. For stiff GeV tracks the local estimate
  degrades (R → huge, curvature → 0 within any window) — but there the creation
  value is already correct to ~10⁻⁴ (gas dE/dx is negligible), so the natural
  rule is hybrid: derived local pT for low-pT tracks, creation pT for stiff 
  ones, with the crossover wherever the local fit's error exceeds the expected
  dE/dx evolution.

  There is a second method worth knowing but only as a cross-check: energy
  bookkeeping — walk the track summing gedep and deplete the creation energy hit
  by hit. It fails as a primary method because gedep sees only ionization in 
  the TPC gas: energy lost upstream (beam pipe, silicon), in delta rays that G4
  tracks separately, and in any non-sensitive material is invisible, and for
  curlers those losses are precisely the ones that matter. The geometric method
  needs none of that accounting — it reads the actual momentum from the actual
  trajectory, all losses included.

  If you want this as data rather than a recipe, it's one post-processing macro:
  read ntp_g4hit, emit per-hit local_pt (and optionally per-cluster via the
  ntp_truth join) — minutes per library chunk, sealed files untouched. Say the
  word and I'll build it.

❯ auto dir = trk->GetVertexMomentumDirection(); is in line 237. What actually   
  does it do?                                                                   

● GetVertexMomentumDirection() returns the particle's momentum direction at the 
  moment it was created — a unit G4ThreeVector, frozen at track birth and never
  updated afterward.

  A G4Track carries two families of kinematic state:

  - Current state — updated at every transport step: trk->GetMomentum(),
  GetMomentumDirection(), GetKineticEnergy() (also reachable per step via
  st->GetPreStepPoint()->GetMomentum()). This is the "local truth" we discussed
  — it changes as the particle loses energy and scatters.
  - Vertex state — written once when the track is spawned and constant forever:
  GetVertexPosition(), GetVertexMomentumDirection(), GetVertexKineticEnergy().
  For a primary, that's the injection state from the HepMC record; for a
  secondary (delta, conversion product…), it's the direction and kinetic energy
  it was born with at its creation point mid-detector — its own, not its
  parent's.

  Geant4 deliberately doesn't store a vertex momentum vector — only the unit
  direction plus the kinetic energy — so the writer reconstructs the vector in
  three lines:

  double ke   = trk->GetVertexKineticEnergy();     // KE at creation
  double m0   = def->GetPDGMass();
  double pmag = std::sqrt(ke * (ke + 2 * m0));     // |p| from relativistic 
  kinematics
  auto   dir  = trk->GetVertexMomentumDirection(); // unit vector at creation
  // gpx,gpy,gpz = dir.{x,y,z}() * pmag / GeV

  The pmag line is just p² = E² − m² with E = KE + m: p = √(KE² + 2·KE·m).
  Multiply the unit direction by that magnitude and you have the full creation
  momentum vector, converted from G4's native MeV to GeV at the fill.

  So this one call is precisely why every hit row of a track carries the same
  gpx/gpy/gpz: the writer never asks the track for its current momentum, only
  for its birth state. Swapping
  GetVertexMomentumDirection/GetVertexKineticEnergy for pre->GetMomentum() is
  the exact one-line change that would turn those columns into per-point local
  truth — the option we evaluated and parked, since it would break the frozen
  container-compatible semantics that transport consumes.

  // :225
  // … midpoint of THIS step's entry and exit points

  // gpx/gpy/gpz ← the TRACK's frozen birth state (same object across all its 
  steps)
  double ke   = trk->GetVertexKineticEnergy();       // :234
  auto   dir  = trk->GetVertexMomentumDirection();   // :237

  ProcessHits runs once per step. The G4Step (st, pre, post) is genuinely
  per-point — each invocation hands a fresh step with new positions, so gx/gy/gz
  naturally differ row to row. The G4Track (trk) is the same particle object
  across all its steps, and the writer queries its vertex accessors — quantities
  stamped at birth and never updated — so every row of that track gets the
  identical momentum.

  The key correction to the framing: it's not that gpx/gpy/gpz cannot be
  per-point — the per-point momentum is sitting right there on the very same
  step object the positions come from:

  pre->GetMomentum()   // exact local momentum at this step — available, 
  deliberately unused

  One line of difference. The writer chooses the track-vertex source to
  reproduce the container's old-eval semantics (momentum as a per-track label —
  the looper cut, truth pT classification — rather than a local kinematic),
  while positions must be per-point because they're the physical payload:
  transport drifts each energy deposit from where it happened. So: same row,
  same fashion of filling — one field family sourced from the step (per-point by
  construction), the other sourced from the track's birth certificate (constant
  by construction), with the per-point alternative available but intentionally
  left on the table.
